# 数据库管理大作业第一阶段需求基线

## 1 项目目标

开发一个基于 MongoDB 的简化在线问卷系统。注册用户能够创建、发布和管理问卷，填写者能够通过公开链接填写问卷，系统能够保存答卷并生成统计结果。

第一阶段重点考察 MongoDB 数据库设计、后端程序设计、业务数据建模、答案校验、条件跳转、测试、项目文档以及 AI 编程过程记录。前端界面可以简单，但系统必须可以运行和演示。

## 2 两阶段开发约束

本项目分两个阶段完成。第一阶段实现初始需求，第二阶段将在第一阶段成果上增加或修改需求。

第一阶段设计必须为后续扩展保留空间。第二阶段不得丢弃第一阶段成果重新实现，不得删除第一阶段主要功能，必须保留核心结构、旧数据和仍然有效的旧功能。

## 3 技术要求

- 后端数据库必须使用 MongoDB。
- 所有业务数据必须存储在 MongoDB 中。
- 不允许使用关系数据库。
- 不允许使用现成的问卷系统框架。
- 第一阶段采用 Node.js、Express、MongoDB 和 Mongoose。
- 身份认证计划采用 JWT，密码计划采用 bcrypt 哈希保存。
- 前端采用简单 HTML、CSS 和 JavaScript，以完整演示功能为目标。
- 测试计划采用自动 API 测试，并补充必要的手工页面测试。

## 4 用户账号与权限

系统必须支持用户注册和登录。每个用户至少包含：

- 用户名
- 密码哈希
- 注册时间

登录用户可以创建问卷、查看自己创建的问卷以及查看这些问卷的统计结果。用户不能查看、修改、发布、关闭或统计其他用户的问卷。

## 5 问卷创建与管理

问卷至少包含：

- 问卷标题
- 问卷说明
- 创建者
- 是否允许匿名填写
- 是否允许同一用户多次提交
- 问卷状态
- 截止时间
- 公开访问码或公开链接
- 创建时间和更新时间

问卷状态至少包括：

- `draft`：草稿，不能公开填写
- `published`：已发布，在截止时间前可以填写
- `closed`：已关闭，不能继续填写

问卷创建者需要能够创建问卷、查看自己的问卷列表、查看和修改问卷、发布问卷、设置截止时间以及关闭问卷。

每份已发布问卷应有类似 `/survey/xxxxxx` 的访问链接。

## 6 题目类型与配置

一份问卷可以包含多个题目，题目必须保存显示顺序。

### 6.1 单选题

- 题目内容
- 多个选项
- 是否必答
- 填写者只能选择一个选项

### 6.2 多选题

- 题目内容
- 多个选项
- 是否必答
- 最少选择数量
- 最多选择数量
- 固定选择数量

固定选择数量可以通过相同的最少和最多选择数量表示。

### 6.3 填空题

填空题分为文本和数字两个子类型。

文本填空支持：

- 是否必答
- 最少字符数
- 最多字符数

数字填空支持：

- 是否必答
- 最小值
- 最大值
- 是否必须为整数

前端可以进行即时校验，但后端必须对所有提交答案重新校验。

## 7 条件跳转

系统必须支持：

- 根据单选题答案跳转
- 根据多选题答案跳转
- 根据数字填空内容跳转
- 没有规则命中时进入下一题

跳转规则必须作为问卷数据存储在 MongoDB 中，不能写死在程序代码里。

后端需要检查：

- 跳转目标题目是否存在
- 目标题目是否属于当前问卷
- 多条规则同时命中时的优先级
- 跳转路径是否形成循环
- 被跳过的必答题不参与最终必答校验

## 8 问卷填写与提交

填写者能够通过问卷链接打开问卷，按顺序回答问题，并根据规则跳转。答案不符合要求时，系统应返回清晰错误信息；完成填写后可以提交，每次成功提交都必须保存。

系统必须支持多人同时填写、匿名填写以及在问卷允许时由同一用户多次填写。

作业原文同时要求填写者登录和支持匿名填写。第一阶段采用以下解释：

- 填写者需要登录。
- 系统内部可以保存填写者标识，用于权限控制和限制重复提交。
- `allowMultipleSubmissions` 控制同一用户是否能够重复提交。

- 问卷允许匿名时，匿名表示对问卷创建者隐藏填写者身份，不表示允许未登录填写。
- 系统内部可以保存 `respondentId`，用于身份认证和限制重复提交。
- 创建者查看匿名答卷、统计结果或调用相关 API 时，响应中不得包含 `respondentId`、用户名等填写者身份信息。
- 匿名保护必须由后端控制返回字段，不能只依靠前端隐藏。

## 9 统计结果

问卷创建者能够查看整份问卷或单道题的统计结果。

单选题统计至少包括：

- 每个选项被选择的人数
- 总回答人数

多选题统计至少包括：

- 每个选项被选择的次数

文本填空统计至少包括：

- 所有已提交文本内容

数字填空统计至少包括：

- 所有已提交数字
- 平均值

统计结果应根据已经保存的答卷自动生成。

## 10 MongoDB 设计要求

不能将所有数据存入一个集合，需要谨慎使用冗余设计，并避免把业务规则写死在程序中。

初步计划使用以下集合：

- `users`：用户账号和注册信息
- `surveys`：问卷基本信息、状态和发布配置
- `questions`：题目、选项、校验配置、顺序和跳转规则
- `responses`：每次提交、填写者信息和答案

正式数据库设计需要说明：

- 集合划分原因
- 嵌入与引用的选择
- 索引设计
- 数据校验方式
- 冗余数据及其一致性处理
- 为什么设计适合 MongoDB
- 为什么没有采用关系数据库结构
- 如何支持第二阶段扩展

## 11 测试要求

至少需要编写以下测试：

- 创建问卷测试
- 添加题目测试
- 跳转逻辑测试
- 答案校验测试
- 提交问卷测试
- 统计结果测试

每个测试用例必须记录：

- 测试目标
- 前置条件
- 操作步骤
- 输入
- 预期输出
- 实际输出
- 测试结果

测试可以是自动测试、API 测试或手工测试。第一阶段优先使用自动 API 测试，并保存关键测试结果作为证据。

| 项目         | 分值 |

| MongoDB 设计 |   35 |


## 15 第一阶段完成判定

只有同时满足以下条件，第一阶段才算完成：

- 所有必需功能可以运行和演示
- 所有业务数据保存在 MongoDB 中
- 权限、答案校验和跳转逻辑由后端保证
- 必需测试已经执行并记录结果
- 代码、配置和启动说明齐全
- 数据库、API、关键逻辑和测试文档齐全
- 第一阶段项目报告完成
- AI 使用日志真实、连续，并能对应实际文件和测试结果
