# 在线问卷系统关键逻辑说明

## 1 文档目的

本文档说明在线问卷系统第一阶段与第二阶段的关键业务逻辑，包括：

- 用户认证；
- 数据所有权；
- 问卷生命周期；
- 四种题型与校验；
- 条件跳转；
- 答卷提交；
- 匿名和重复提交；
- 题目复用；
- 题目版本；
- 题目共享；
- 题目库；
- 题目使用情况；
- 跨问卷统计；
- 第一阶段旧数据迁移；
- 测试数据库隔离。

系统采用 Node.js、Express、MongoDB 和 Mongoose 实现，业务数据全部保存在 MongoDB 中。

---

## 2 系统结构

系统采用前后端分离程度较低的 Web 结构：

```text
浏览器页面
   │
   │ HTTP + JSON
   ▼
Express 路由
   │
   ▼
认证中间件
   │
   ▼
Controller 控制器
   │
   ▼
Service 业务校验
   │
   ▼
Mongoose Model
   │
   ▼
MongoDB
```

主要目录：

```text
public/                  浏览器页面、CSS 和 JavaScript
src/routes/              API 路由
src/controllers/         控制器和业务流程
src/middleware/          JWT 认证中间件
src/services/            答案和填写路径校验
src/models/              Mongoose 数据模型
scripts/                 第二阶段迁移脚本
tests/                   Jest 和 Supertest 自动化测试
docs/                    项目文档
```

## 3 用户认证逻辑

### 3.1 注册

用户提交用户名和密码后，后端按以下顺序处理：

1. 检查用户名和密码是否为合法字符串；
2. 检查密码长度是否达到最低要求；
3. 使用 `bcrypt.truncates(password)` 检查密码是否超过 bcrypt 支持的 72 个 UTF-8 字节；
4. 查询用户名是否已存在；
5. 使用 bcrypt 生成密码哈希；
6. 将用户名和 `passwordHash` 保存到 MongoDB；
7. 返回用户 ID、用户名和创建时间；
8. 不返回密码原文或密码哈希。

用户名通过唯一索引保证不重复。

### 3.2 登录

登录流程：

1. 根据用户名查询用户；
2. 显式读取默认隐藏的 `passwordHash`；
3. 使用 bcrypt 比较密码；
4. 验证成功后签发 JWT；
5. JWT 中保存用户 ID；
6. 返回令牌和安全的用户信息。

用户名不存在和密码错误统一返回“用户名或密码错误”，避免泄露用户名是否存在。

### 3.3 JWT 认证中间件

受保护接口使用：

```http
Authorization: Bearer <token>
```

认证中间件负责：

1. 读取 Authorization 请求头；
2. 检查 Bearer 格式；
3. 使用 `JWT_SECRET` 验证令牌；
4. 从令牌中取得用户 ID；
5. 查询用户是否仍然存在；
6. 将安全用户信息保存到 `req.user`；
7. 认证失败时返回 `401`。

业务控制器只能使用认证中间件写入的 `req.user.id`，不能信任客户端提交的 `ownerId`。

## 4 数据所有权保护

### 4.1 问卷所有权

问卷管理接口使用：

```text
Survey._id = surveyId
Survey.ownerId = req.user.id
```

同时查询问卷。

用户访问他人问卷时返回 `404`，而不是明确提示问卷属于其他用户，以减少资源信息泄露。

### 4.2 可复用题目所有权

可复用题目的创建版本、恢复版本、查看发出共享和查询完整使用情况等操作，需要满足：

```text
QuestionItem.ownerId = req.user.id
```

共享接收者只有 `use` 权限，不能取得所有者权限。

### 4.3 题目库所有权

题目库接口必须同时验证：

```text
QuestionBank._id = bankId
QuestionBank.ownerId = req.user.id
```

题目加入题目库时，还要验证逻辑题目属于当前用户。

### 4.4 跨问卷统计权限

跨问卷统计只查询：

```text
Survey.ownerId = req.user.id
```

对应的问卷。

因此：

- 逻辑题目所有者不能查看其他用户问卷中的答卷；
- 共享接收者只能统计本人问卷中的数据；
- 不实现跨用户答卷统计；
- 不因题目被共享而扩大答卷读取权限。

## 5 问卷生命周期

问卷状态：

```text
draft → published → closed
```

### 5.1 draft

草稿状态允许：

- 创建题目；
- 编辑题目；
- 删除题目；
- 设置跳转规则；
- 从本人可复用题目加入指定版本；
- 从收到的共享中加入指定版本；
- 从题目库加入指定版本。

### 5.2 published

发布后：

- 可以通过公开链接读取；
- 登录用户可以提交答卷；
- 不允许继续修改题目结构；
- 不允许继续从题库或可复用题目加入新题；
- 已保存的题目快照保持稳定。

### 5.3 closed

关闭后：

- 不能公开读取和提交；
- 历史答卷继续保留；
- 统计功能继续可用；
- 问卷、题目快照和答卷不进行级联删除。

### 5.4 数据保留

已经发布或关闭的问卷不物理删除。

关闭问卷只改变状态，不删除：

- Question 题目实例；
- Response 答卷；
- 答案快照；
- 题目版本引用；
- 统计所需历史数据。

## 6 第一阶段题目结构

第一阶段支持四种题型：

```text
singleChoice
multipleChoice
text
number
```

### 6.1 选择题

单选题和多选题使用：

```text
options[] = {
  optionId,
  label
}
```

`optionId` 是稳定标识。修改选项文字时可以保留原 `optionId`，保证已有跳转规则和答案快照仍然能够识别原选项。

### 6.2 validation 按题型保存

不同题型只保存适用的校验字段。

单选题：

```text
不保存额外 validation 字段
```

多选题：

```text
minSelections
maxSelections
```

文本题：

```text
minLength
maxLength
```

数字题：

```text
minValue
maxValue
integerOnly
```

这样可以减少 MongoDB 文档冗余，避免接口使用者误解无关字段。

### 6.3 问卷专属字段

以下字段属于问卷中的题目实例，不属于可复用题目版本：

```text
surveyId
order
required
jumpRules
```

这些字段由 Question 管理，不进入 QuestionVersion。

## 7 条件跳转逻辑

### 7.1 跳转规则结构

跳转规则保存在题目实例的 `jumpRules` 中。

跳转到其他题目：

```text
optionId
action = goto
targetQuestionId
```

提前提交：

```text
optionId
action = submit
```

### 7.2 跳转优先级

填写过程中：

1. 读取当前题目的答案；
2. 按规则顺序检查是否命中；
3. 命中 `goto` 时进入目标题目；
4. 命中 `submit` 时结束填写路径；
5. 没有命中规则时进入下一道顺序题；
6. 没有下一题时结束。

### 7.3 跳转目标限制

第一阶段采用只向后跳转的规则：

```text
targetQuestion.order > currentQuestion.order
```

因此不允许：

- 跳转到当前题；
- 跳转到前面的题；
- 跨问卷跳转；
- 跳转到不存在的题。

原有有向图循环检测继续保留，作为额外保护。

只向后跳转也能避免以下隐含循环：

```text
第 3 题 goto 第 2 题
第 2 题默认顺序进入第 3 题
```

### 7.4 被引用题目删除保护

如果其他题目的跳转规则引用某道题，则该题不能直接删除。

用户必须先删除或修改相关跳转规则。

---

## 8 填写路径与答案校验

### 8.1 路径计算

后端不能直接相信客户端提交的 `visitedQuestionIds`。

提交答卷时，后端根据以下数据重新计算合法路径：

- 问卷题目顺序；
- 用户答案；
- 选项 ID；
- 跳转规则；
- `goto` 和 `submit` 行为。

计算结果用于检查客户端路径是否真实。

### 8.2 跳过题目的答案

如果题目因条件跳转没有出现在合法路径中，客户端不能为该题提交额外答案。

这样可防止绕过前端直接构造请求。

### 8.3 必答题

只有实际路径中出现的必答题需要回答。

被跳转规则跳过的必答题不要求填写。

### 8.4 四种题型校验

单选题：

- 值必须是字符串；
- `optionId` 必须属于当前题目。

多选题：

- 值必须是数组；
- 每个 `optionId` 必须属于当前题目；
- 不能包含重复选项；
- 选择数量必须满足最小值和最大值。

文本题：

- 值必须是字符串；
- 长度必须满足 `minLength` 和 `maxLength`。

数字题：

- 值必须是有限数字；
- 必须满足最小值和最大值；
- `integerOnly=true` 时必须是整数。

## 9 答卷、匿名与重复提交

### 9.1 登录要求

填写问卷前必须登录。

匿名不表示允许未登录填写。

### 9.2 匿名含义

匿名表示：

```text
对问卷创建者隐藏填写者身份
```

系统内部可以保存 `respondentId`，用于：

- 登录认证；
- 重复提交限制；
- 系统内部数据一致性。

但是创建者查看匿名答卷、统计或调用相关 API 时，不得获得：

- `respondentId`
- 答卷者用户名
- `uniqueSubmissionKey`

匿名保护由后端控制返回字段，不能只依赖前端隐藏。

### 9.3 重复提交

开启重复提交限制时，系统构造：

```text
uniqueSubmissionKey =
surveyId + ":" + respondentId
```

通过 sparse 唯一索引阻止同一用户重复提交。

未开启限制时，不设置该字段，因此允许重复提交。

### 9.4 答案快照

每个答案保存：

```text
questionId
questionItemId
questionVersionId
questionType
questionTitle
value
optionSnapshots
```

选择题的 `optionSnapshots` 保存：

```text
optionId
label
```

即使以后题目文字或选项发生变化，历史答卷仍然能够解释当时提交的内容。

### 9.5 答卷 schemaVersion

第一阶段旧答卷继续使用：

```text
schemaVersion = 1
```

使用完整第二阶段题目引用的新答卷使用：

```text
schemaVersion = 2
```

兼容原则：

- 旧数据继续可读；
- 新答案尽量保存 `questionItemId` 和 `questionVersionId`；
- 不强制重写已经存在的历史答案。

## 10 第二阶段逻辑题目模型

第二阶段把“逻辑题目”和“题目内容版本”分开保存。

```text
QuestionItem 1 ─── N QuestionVersion
```

### 10.1 QuestionItem

QuestionItem 表示逻辑题目身份，主要保存：

```text
ownerId
currentVersionId
latestVersionNumber
status
legacyQuestionId
schemaVersion
```

它不直接保存完整题目正文。

### 10.2 QuestionVersion

QuestionVersion 保存某个版本的题目内容：

```text
questionItemId
versionNumber
parentVersionId
restoredFromVersionId
createdByUserId
changeNote
type
title
options
validation
schemaVersion
```

唯一约束：

```text
questionItemId + versionNumber
```

同一逻辑题目的版本号不能重复。

---

## 11 历史版本不可变

### 11.1 不提供修改和删除接口

系统不提供以下接口：

```text
PATCH QuestionVersion
DELETE QuestionVersion
```

历史版本创建后不再原地修改。

### 11.2 创建新版本

编辑可复用题目时：

1. 读取当前版本；
2. 生成 `latestVersionNumber + 1`；
3. 新版本的 `parentVersionId` 指向原当前版本；
4. 保存新 QuestionVersion；
5. 使用条件更新修改 QuestionItem；
6. 将 `currentVersionId` 指向新版本；
7. 增加 `latestVersionNumber`。

### 11.3 并发冲突

更新 QuestionItem 时，同时匹配旧的：

```text
currentVersionId
latestVersionNumber
```

如果其他请求已经先创建版本，条件更新失败并返回 `409`。

创建失败时会删除本次尚未正式采用的新版本，避免留下孤立记录。

### 11.4 恢复历史版本

恢复历史版本时不把 `currentVersionId` 直接改回旧版本。

系统执行：

1. 读取指定历史版本；
2. 复制历史版本的题型、标题、选项和校验；
3. 创建新的递增版本；
4. `parentVersionId` 指向恢复前当前版本；
5. `restoredFromVersionId` 指向被恢复的历史版本；
6. 将新版本设为当前版本。

这样既恢复了内容，又保留完整版本时间线。

---

## 12 指定版本复用和题目快照

### 12.1 显式选择版本

将可复用题目加入问卷时，客户端必须提供：

```text
questionItemId
questionVersionId
required
```

后端不能只动态读取 `QuestionItem.currentVersionId`，因为当前版本可能在请求前后发生变化。

### 12.2 快照复制

加入问卷时，后端把指定 QuestionVersion 的以下内容复制到 Question：

```text
type
title
options
validation
```

同时保存：

```text
questionItemId
questionVersionId
contentSource = library
schemaVersion = 2
```

问卷专属字段由 Question 单独管理：

```text
surveyId
order
required
jumpRules
```

### 12.3 旧问卷不自动升级

QuestionItem 创建新版本后：

- `currentVersionId` 发生变化；
- 已有 Question 的 `questionVersionId` 不变；
- 已有 Question 的内容快照不变；
- 已发布问卷不受影响；
- 已有答卷不受影响。

如果用户希望在草稿问卷采用新版本，应重新明确选择版本，而不是自动同步。

---

## 13 题目使用情况

使用情况根据 Question 中的：

```text
questionItemId
questionVersionId
surveyId
```

查询。

接口返回：

- 使用次数；
- 涉及问卷数量；
- 使用过的版本；
- 问卷状态；
- 题目实例顺序；
- 是否必答；
- 问卷中的内容快照。

使用情况只查询当前用户本人拥有的问卷。

---

## 14 题目共享逻辑

### 14.1 唯一共享关系

共享关系使用唯一索引：

```text
questionItemId + sharedWithUserId
```

同一逻辑题目与同一接收者之间只保留一条共享记录。

### 14.2 共享权限

当前仅实现：

```text
permission = use
```

接收者可以：

- 查看收到的有效共享；
- 查看共享题目的版本；
- 将指定版本加入本人草稿问卷。

接收者不能：

- 修改所有者题目；
- 创建新版本；
- 恢复历史版本；
- 归档所有者题目；
- 撤销所有者发出的共享；
- 转发共享权限。

### 14.3 软撤销

撤销共享时：

```text
status = revoked
revokedAt = 当前时间
```

不物理删除共享记录。

撤销后的效果：

- 接收者不能继续新复用；
- 已加入问卷的 Question 快照不删除；
- 已发布问卷不受影响；
- 历史答卷不受影响。

### 14.4 重新激活

再次共享给同一用户时：

1. 查找原共享记录；
2. 将 `status` 改回 `active`；
3. 清除 `revokedAt`；
4. 更新 `sharedAt`；
5. 不创建重复共享关系。

时间语义：

- `createdAt`：首次创建共享记录的时间；
- `sharedAt`：最近一次激活时间；
- 重复提交已经 active 的共享时不更新时间；
- revoked 重新激活时才更新 `sharedAt`。

---

## 15 题目库逻辑

### 15.1 最小题目库功能

第二阶段只实现：

- 创建本人题目库；
- 查询列表和详情；
- 修改名称与说明；
- 加入本人逻辑题目；
- 移除题目；
- 设置推荐版本；
- 从题目库把指定版本加入本人草稿问卷。

不实现：

- 题目库共享；
- 公开市场；
- 标签系统；
- 复杂搜索；
- 拖拽排序；
- 高级归档。

### 15.2 引用式存储

题目库只保存：

```text
questionItemId
preferredVersionId
order
addedAt
```

不复制题目正文。

题目正文由 QuestionVersion 统一保存。

### 15.3 推荐版本

`preferredVersionId` 只是以后选题时的建议版本。

修改推荐版本：

- 不改变 QuestionItem 当前版本；
- 不改变已加入问卷的 Question；
- 不改变历史答卷；
- 不自动升级任何问卷。

### 15.4 从题目库移除

移除只删除 QuestionBank.items 中的引用。

不会删除：

- QuestionItem；
- QuestionVersion；
- Question；
- Response；
- 已有问卷快照。

### 15.5 sparse 唯一索引兼容

`legacyQuestionId` 使用 sparse 唯一索引。

新建第二阶段逻辑题目时，该字段应保持不存在，而不是显式保存为 `null`，否则多个 `null` 可能触发唯一索引冲突。

## 16 跨问卷统计

### 16.1 权限边界

跨问卷统计先查询：

```text
Survey.ownerId = req.user.id
```

只统计当前用户拥有的问卷。

共享题目不会授权题目所有者查看接收者问卷的答卷。

### 16.2 按版本分组

同一逻辑题目的不同版本可能具有：

- 不同题型；
- 不同选项；
- 不同 validation；
- 不同题目文字。

因此具体统计按：

```text
questionVersionId
```

分组，不强行合并不同版本。

接口也支持通过 `questionVersionId` 查询指定版本。

### 16.3 responseCount

`responseCount` 表示纳入统计的本人问卷去重答卷总数。

同一份答卷即使包含多个相同逻辑题目的实例，也只计为一份答卷。

### 16.4 answerOpportunityCount

同一逻辑题目可能：

- 在多个问卷中出现；
- 在同一问卷中出现多个实例；
- 使用不同版本。

因此回答机会数计算为：

```text
各题目实例所在问卷的答卷数之和
```

即：

```text
answerOpportunityCount =
Σ 每个题目实例对应问卷的答卷数
```

### 16.5 notAnsweredCount

未回答数计算为：

```text
notAnsweredCount =
answerOpportunityCount - totalAnswers
```

不能简单使用：

```text
responseCount - totalAnswers
```

因为一个答卷可能对应同一逻辑题目的多个题目实例。

### 16.6 四种题型统计

单选题：

- 按同一版本的稳定 `optionId` 计数；
- 不只按选项文字合并。

多选题：

- 每份有效答案计入 `totalAnswers`；
- 每个被选择的 `optionId` 分别增加计数。

文本题：

- 返回文本回答列表；
- 不返回答卷者身份。

数字题：

- 返回有效数字列表；
- 计算平均值；
- 计算最小值；
- 计算最大值。

### 16.7 敏感字段

跨问卷统计不得返回：

```text
respondentId
答卷者 username
uniqueSubmissionKey
passwordHash
```

## 18 错误处理

### 18.1 JSON 解析错误

非法 JSON 返回：

```text
400 Bad Request
```

而不是 `500`。

### 18.2 Mongoose 校验错误

Schema 校验失败时返回 `400`，并返回可理解的错误信息。

### 18.3 唯一索引冲突

用户名、版本号、共享关系或题目库名称等唯一索引冲突返回：

```text
409 Conflict
```

### 18.4 资源不存在或越权

资源不存在与无权访问通常统一返回：

```text
404 Not Found
```

### 18.5 状态冲突

以下情况通常返回 `409`：

- 发布后继续编辑题目；
- 已关闭问卷继续操作；
- 重复提交答卷；
- 题目版本发生并发冲突。

系统遵守以下数据保留原则：

1. 已发布或关闭问卷不物理删除；

9. 统计基于实际保存的快照和版本引用；
10. 涉及身份信息的字段不得通过统计接口泄露。

# 问卷系统关键逻辑说明

## 1 文档目的

本文档说明问卷系统第一阶段实现中的关键业务逻辑，包括身份认证、数据权限、问卷状态、题目校验、条件跳转、答卷提交、匿名保护、重复提交控制、数据快照、统计计算和自动化测试隔离。

接口路径、请求字段和响应结构参见 `docs/API说明.md`，MongoDB 集合和索引参见 `docs/数据库设计.md`。

## 2 系统结构

项目采用前后端分层结构。

```text
浏览器页面
    ↓ HTTP/JSON
Express 路由
    ↓
身份认证中间件
    ↓
控制器
    ↓
业务校验服务
    ↓
Mongoose 模型
    ↓
MongoDB
```

各层职责如下：

- `public/`：注册、登录、问卷管理、题目管理、公开填写和统计页面。
- `src/routes/`：声明 API 路径，并为受保护接口加载认证中间件。
- `src/middleware/auth.js`：验证 JWT，读取当前登录用户。
- `src/controllers/`：处理问卷、题目、跳转、答卷和统计业务。
- `src/services/responseValidationService.js`：校验答案并计算实际填写路径。
- `src/models/`：定义 MongoDB 文档结构、字段校验和索引。

前端用于改善交互体验，后端负责最终校验。即使绕过前端直接调用 API，也必须通过后端的身份、权限、题型和业务规则检查。

## 3 用户认证逻辑

### 3.1 用户注册

注册接口首先处理用户名和密码：

1. 用户名去除首尾空格。
2. 用户名转换为小写。
3. 用户名长度必须为 3～30 个字符。
4. 密码不能少于 8 个字符。
5. 使用 `bcrypt.truncates(password)` 检查密码是否超过 bcrypt 支持的 72 个 UTF-8 字节。
6. 检查用户名是否已经存在。
7. 使用 bcrypt 的 12 轮成本参数生成密码哈希。
8. 只把 `passwordHash` 保存到 MongoDB，不保存明文密码。
9. 注册成功后生成 JWT。

`users.username` 建立了唯一索引。控制器的存在性检查用于向用户返回明确错误，MongoDB 唯一索引用于处理并发注册造成的冲突。

### 3.2 用户登录

登录时：

1. 对用户名执行和注册相同的去空格、转小写处理。
2. 使用 `.select('+passwordHash')` 显式读取默认不返回的密码哈希。
3. 使用 `bcrypt.compare` 比较用户输入和密码哈希。
4. 用户不存在和密码错误统一返回“用户名或密码错误”，避免泄露某个用户名是否存在。
5. 登录成功后签发 JWT。

### 3.3 JWT 校验

JWT 的有效载荷使用 `sub` 保存用户 ID。

受保护接口要求请求头包含：

```http
Authorization: Bearer <JWT>
```

认证中间件依次检查：

1. 是否存在 `Bearer` 请求头。
2. 令牌内容是否为空。
3. JWT 签名和有效期是否正确。
4. 令牌中的用户是否仍然存在。

验证成功后，中间件把以下信息写入 `req.user`：

```json
{
  "id": "当前用户ID",
  "username": "当前用户名"
}
```

后续控制器使用 `req.user.id` 判断资源所有权。

密码哈希不会通过注册、登录或当前用户接口返回。

## 4 数据权限控制

系统的主要权限规则是“创建者只能管理自己的问卷”。

查询受保护资源时，控制器同时使用资源 ID 和当前用户 ID：

```javascript
{
  _id: surveyId,
  ownerId: req.user.id
}
```

这项规则应用于：

- 本人问卷列表；
- 问卷发布；
- 问卷关闭；
- 题目创建；
- 题目查看；
- 题目编辑；
- 题目删除；
- 跳转规则配置；
- 问卷统计。

当问卷不存在或不属于当前用户时，接口统一返回 404。这样既阻止越权访问，也减少了通过不同错误信息判断他人资源是否存在的可能。

公开问卷读取接口不要求登录，但只返回填写页面需要的数据，不返回：

- `ownerId`；
- 创建者用户名；
- 问卷内部 `_id`；
- 答卷数据；
- 填写者身份。

答卷提交接口必须登录。公开链接只表示可以公开读取问卷内容，不表示可以免登录提交。

## 5 问卷状态与生命周期

问卷状态包括：

```text
draft → published → closed
```

### 5.1 草稿状态

新问卷默认处于 `draft` 状态。

草稿状态允许：

- 添加题目；
- 编辑题目；
- 删除题目；
- 配置跳转规则。

草稿问卷不能通过公开接口读取或提交答卷。

### 5.2 发布状态

问卷发布前必须满足：

- 问卷属于当前用户；
- 当前状态为 `draft`；
- 至少包含一道题；
- 截止时间尚未到达；
- 所有 `goto` 目标属于当前问卷；
- 跳转规则不存在循环。

发布成功后：

- 状态改为 `published`；
- 设置 `publishedAt`；
- 公开链接可以读取问卷；
- 登录用户可以提交答卷；
- 题目和跳转规则进入只读状态。

### 5.3 关闭状态

只有 `published` 问卷可以关闭。

关闭后：

- 状态改为 `closed`；
- 设置 `closedAt`；
- 公开接口不再返回问卷；
- 不再接受新答卷；
- 已保存的答卷和统计数据继续保留。

已发布或已关闭问卷不进行物理删除，以保护历史答卷和统计结果。

### 5.4 截止时间

公开读取和提交答卷时都会检查截止时间。

当问卷超过截止时间后，接口返回 410。即使问卷状态仍然是 `published`，也不能继续填写。

## 6 题目、选项与校验配置

系统支持四种题型：

| 题型   | 标识               |
| ------ | ------------------ |
| 单选题 | `singleChoice`   |
| 多选题 | `multipleChoice` |
| 文本题 | `text`           |
| 数字题 | `number`         |

### 6.1 题目顺序

创建题目时，服务端根据当前问卷已有题目的最大 `order` 生成下一顺序。

MongoDB 使用下面的唯一复合索引：

```javascript
{ surveyId: 1, order: 1 }
```

该索引保证同一问卷中不能存在两道顺序相同的题目。并发创建造成顺序冲突时，接口返回 409，提示重新提交。

### 6.2 选择题选项

每个选择题选项包含：

```json
{
  "optionId": "稳定选项标识",
  "label": "选项文字"
}
```

未提供 `optionId` 时，服务端自动生成。

编辑选择题时，前端应传回已有的 `optionId`。这样即使选项文字发生变化，跳转规则和历史答卷仍然可以通过稳定标识识别该选项。

同一道题中不允许出现重复的 `optionId`。

### 6.3 按题型保存校验字段

四种题型共用 MongoDB 中的 `validation` 子文档，但控制器会按题型筛选字段：

| 题型               | 保存的校验字段                              |
| ------------------ | ------------------------------------------- |
| `singleChoice`   | 不保存校验字段                              |
| `multipleChoice` | `minSelections`、`maxSelections`        |
| `text`           | `minLength`、`maxLength`                |
| `number`         | `minValue`、`maxValue`、`integerOnly` |

创建、编辑、管理端序列化和公开端序列化都会执行规范化。

这样可以避免多选题出现 `integerOnly`、文本题出现 `minValue` 等无关字段，减少文档冗余和接口歧义。

### 6.4 Schema 校验

Mongoose Schema 继续执行底层校验：

- 单选题和多选题至少包含两个选项；
- 文本题和数字题不能包含选项；
- 同一道题的 `optionId` 不能重复；
- `minSelections` 不能大于 `maxSelections`；
- `minLength` 不能大于 `maxLength`；
- `minValue` 不能大于 `maxValue`；
- `goto` 规则必须包含目标题目；
- `submit` 规则不能包含目标题目。

控制器校验负责返回清晰的业务错误，Schema 校验负责保护最终写入 MongoDB 的数据。

## 7 条件跳转逻辑

### 7.1 规则存储

跳转规则存储在题目的 `jumpRules` 数组中，没有写死在前端或后端代码中。

每条规则包含：

```json
{
  "operator": "equals",
  "value": "条件值",
  "action": "goto",
  "targetQuestionId": "目标题目ID",
  "priority": 0
}
```

`action` 支持：

- `goto`：跳转到目标题目；
- `submit`：提前结束问卷并提交。

### 7.2 各题型操作符

| 题型   | 操作符                                       |
| ------ | -------------------------------------------- |
| 单选题 | `equals`                                   |
| 多选题 | `containsAny`、`containsAll`             |
| 文本题 | `equals`                                   |
| 数字题 | `equals`、`gt`、`gte`、`lt`、`lte` |

含义如下：

- `equals`：答案与规则值相等；
- `containsAny`：多选答案包含规则数组中的任意一项；
- `containsAll`：多选答案包含规则数组中的全部项目；
- `gt`：大于；
- `gte`：大于或等于；
- `lt`：小于；
- `lte`：小于或等于。

### 7.3 优先级

同一道题的规则按照 `priority` 从小到大排列。

运行时只执行第一条命中的规则。为了避免结果不确定，同一道题不允许两个规则使用相同的优先级。

如果没有规则命中，系统进入顺序中的下一题。

### 7.4 跳转目标保护

保存规则时会检查：

- `goto` 必须提供合法的 `targetQuestionId`；
- 目标题必须属于同一问卷；
- 不能跳转到当前题；
- 只能跳转到 `order` 更大的后续题目；
- `submit` 不能设置目标题目。

只允许向后续题目跳转，可以保证填写路径持续向前，避免显式跳转和默认下一题路径共同形成隐含循环。

### 7.5 循环检测

系统同时保留显式跳转图的循环检测。

处理方式为：

1. 把每道题作为有向图节点。
2. 把每条 `goto` 规则作为有向边。
3. 使用深度优先搜索记录节点访问状态。
4. 如果搜索过程中再次进入正在访问的节点，则判断存在循环。
5. 配置规则和发布问卷时都会检查循环。

“只允许向后跳转”和“有向图循环检测”共同保护填写流程。

### 7.6 被引用题目删除保护

删除题目前，系统会查询是否有其他题目的 `goto` 规则指向它。

如果仍被引用，删除操作返回 409。创建者需要先删除或修改相应规则，再删除题目，避免产生失效目标。

## 8 答案校验与填写路径计算

后端的 `buildSubmission` 负责校验答案并重新计算填写路径。前端提交的路径不能直接作为可信依据。

### 8.1 输入结构检查

服务端首先检查：

- `answers` 必须是数组；
- 每个答案必须是对象；
- 每个答案必须包含字符串形式的 `questionId`；
- 每个答案必须包含 `value`；
- 题目必须属于当前问卷；
- 同一道题不能提交多个答案。

### 8.2 各题型答案校验

单选题：

- 答案必须是字符串；
- 答案必须是当前题目的有效 `optionId`。

多选题：

- 答案必须是字符串数组；
- 数组不能包含重复选项；
- 每个选项必须属于当前题目；
- 选择数量必须符合 `minSelections` 和 `maxSelections`。

文本题：

- 答案必须是字符串；
- 保存前去除首尾空格；
- 长度必须符合 `minLength` 和 `maxLength`。

数字题：

- 答案必须是有限数字；
- `integerOnly` 为 `true` 时必须是整数；
- 数值必须符合 `minValue` 和 `maxValue`。

### 8.3 路径计算过程

服务端从第一题开始依次处理：

1. 把当前题加入 `visitedQuestionIds`。
2. 判断当前题是否已回答。
3. 如果当前题必答但没有有效答案，则拒绝提交。
4. 对答案执行当前题型的校验。
5. 按优先级检查跳转规则。
6. 命中 `submit` 时结束路径。
7. 命中 `goto` 时进入目标题目。
8. 没有命中规则时进入顺序中的下一题。
9. 直到提前提交或没有下一题。

系统还使用访问集合检测运行时重复进入同一道题。如果出现异常循环，提交会被拒绝。

### 8.4 被跳过题目的处理

路径计算完成后，系统检查提交中是否包含未访问题目的答案。

如果包含，返回：

```text
答案包含填写路径中未访问的题目
```

被条件跳转跳过的必答题不参与必答校验，因为它不在本次真实填写路径中。

这项规则同时解决了两个问题：

- 不能通过额外提交隐藏题目数据绕过流程；
- 不会错误要求用户回答条件跳转已经跳过的题目。

### 8.5 前端路径变化

公开填写页面支持上一题。

用户返回前面题目并修改答案后，前端会删除原路径后方的答案，并根据新答案重新计算后续路径。

提交时，后端仍会从头重新计算一次，以防止前端状态被修改或伪造。

## 9 匿名、重复提交和历史快照

### 9.1 匿名的含义

系统中的匿名表示：

> 对问卷创建者隐藏填写者身份。

匿名不表示免登录填写。提交答卷前仍然需要登录。

系统内部保存 `respondentId`，用于：

- 验证填写者身份；
- 限制同一用户重复提交；
- 保证数据完整性。

创建者查看统计结果时，接口不返回：

- `respondentId`；
- 答卷者用户名；
- `uniqueSubmissionKey`；
- 单份答卷对应的身份信息。

匿名保护由后端响应字段控制，不能只依靠前端隐藏。

### 9.2 重复提交控制

当问卷不允许重复提交时，答卷保存：

```text
uniqueSubmissionKey = surveyId:respondentId
```

`responses` 集合对该字段建立：

```javascript
{ unique: true, sparse: true }
```

唯一索引保证同一用户不能为同一问卷保存第二份答卷。即使两个请求同时到达，MongoDB 仍会拒绝重复键。

当问卷允许重复提交时，不设置 `uniqueSubmissionKey`。由于索引是稀疏索引，多份不包含该字段的答卷可以正常保存。

### 9.3 题目和选项快照

每个答案除保存 `questionId` 和实际值外，还保存：

- `questionType`；
- `questionTitle`；
- `optionSnapshots`。

选择题快照包含提交时的：

- `optionId`；
- `label`。

这样即使第二阶段修改题目文字或选项文字，历史答卷仍能解释提交时用户看到的内容。

答卷还保存：

- `visitedQuestionIds`：本次实际访问路径；
- `surveyVersion`：提交时的问卷数据版本；
- `submittedAt`：提交时间。

问卷关闭或以后调整题目时，不级联删除历史答卷。

## 10 统计逻辑

### 10.1 权限保护

统计接口需要登录，并且使用问卷 ID 和当前用户 ID 查询问卷。

只有问卷创建者可以查看统计。其他用户访问时返回 404。

统计响应不返回填写者身份字段。

### 10.2 MongoDB 聚合

统计控制器同时执行：

1. `Response.countDocuments` 统计问卷答卷总数；
2. MongoDB 聚合管道收集每道题的答案值。

聚合管道主要步骤为：

```javascript
[
  {
    $match: {
      surveyId: survey._id
    }
  },
  {
    $unwind: '$answers'
  },
  {
    $group: {
      _id: '$answers.questionId',
      values: {
        $push: '$answers.value'
      }
    }
  }
]
```

MongoDB 负责按题目分组答案，Node.js 根据题型构造最终统计结果。

### 10.3 通用数量

整份问卷的答卷数量为：

```text
responseCount
```

每道题包含：

```text
totalAnswers
notAnsweredCount
```

计算关系为：

```text
notAnsweredCount = responseCount - totalAnswers
```

`notAnsweredCount` 不命名为 `skippedCount`，因为未回答可能有两种原因：

- 条件跳转没有经过该题；
- 该题不是必答题，填写者主动未填写。

### 10.4 各题型统计

单选题：

- 返回每个选项的 `optionId`、`label` 和 `count`；
- 每份有效答案只增加一个选项计数。

多选题：

- 返回每个选项的选择次数；
- 同一份答卷可以同时增加多个选项计数。

文本题：

- 返回有效文本答案的 `values` 列表；
- 统计页面逐条显示文本内容。

数字题：

- 过滤非数字和非有限值；
- 返回数字答案数量；
- 返回 `values`；
- 返回 `average`；
- 没有有效数字时，`average` 为 `null`。

统计 API 返回数字列表和平均值。统计前端根据 `values` 计算并显示最小值和最大值。

### 10.5 单题筛选

统计接口接受：

```text
questionId
```

提供该参数时：

- `responseCount` 仍是整份问卷的答卷总数；
- `questionCount` 为 1；
- `questions` 只返回指定题目；
- 题目必须属于当前问卷。

## 11 错误处理

系统根据错误类型使用不同 HTTP 状态码：

| 状态码  | 使用情况                         |
| ------- | -------------------------------- |
| `200` | 查询或修改成功                   |
| `201` | 创建资源或提交答卷成功           |
| `400` | 请求字段、答案或业务校验失败     |
| `401` | 缺少令牌、令牌无效或用户不存在   |
| `404` | 资源不存在或不属于当前用户       |
| `409` | 状态冲突、重复提交或唯一索引冲突 |
| `410` | 问卷超过截止时间                 |
| `500` | 未处理的服务器内部错误           |

业务错误统一返回：

```json
{
  "message": "具体错误原因"
}
```

Mongoose `ValidationError` 会整理成可读信息并返回 400。

MongoDB 唯一索引冲突根据业务位置转换为：

- 用户名重复；
- 问卷公开编号冲突；
- 同一用户重复提交。

没有匹配到路由时返回 404。未处理异常由 Express 全局错误处理中间件返回 500。

## 12 自动化测试隔离

自动化测试使用：

- Jest；
- Supertest；
- 独立测试服务器；
- 独立测试数据库。

测试服务器使用：

```text
http://127.0.0.1:3101
```

测试数据库使用：

```text
questionnaire_system_test
```

测试启动过程：

1. Jest 的 `globalSetup` 启动独立子进程。
2. 子进程连接测试数据库。
3. 检查当前数据库名称必须是 `questionnaire_system_test`。
4. 测试前清空测试数据库。
5. 启动 3101 端口测试服务器。
6. 子进程发送 `ready` 消息后，Jest 才开始运行测试。

测试结束过程：

1. `globalTeardown` 向测试服务器发送关闭消息。
2. 测试服务器停止监听端口。
3. 再次确认数据库名称。
4. 清理测试数据库。
5. 断开 MongoDB 连接并退出子进程。

数据库名称保护可以避免测试代码误删开发数据库 `questionnaire_system`。

当前自动化测试覆盖：

- 健康接口；
- 不存在接口的 404；
- 创建问卷；
- 添加题目；
- 合法向后跳转；
- 非法向前跳转；
- 无效选项校验；
- 提交答卷；
- 实际路径记录；
- 重复提交保护；
- 统计结果；
- 单题统计；
- 未登录访问保护；
- 跨用户访问保护；
- 敏感身份字段保护。

## 13 数据保留与第二阶段兼容

第一阶段采用以下数据保留策略：

- 已发布或已关闭的问卷不物理删除；
- 题目只能在草稿状态编辑和删除；
- 问卷关闭后保留全部答卷；
- 题目变化不级联删除历史答卷；
- 答卷保存题目和选项快照；
- 问卷和答卷保存版本字段。

这些设计为第二阶段的数据结构变化预留了基础。后续如需升级 Schema，可以根据 `schemaVersion` 判断旧数据版本，并通过迁移脚本或兼容读取逻辑处理历史数据。
