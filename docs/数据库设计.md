# 问卷系统 MongoDB 数据库设计

## 1 设计目标

数据库需要支持用户账号、问卷管理、多种题型、答案校验、条件跳转、
问卷填写和统计，并为第二阶段需求变化保留扩展能力。

系统使用 MongoDB，不使用关系数据库。业务数据划分为 users、surveys、
questions 和 responses 四个集合，避免将所有数据放入同一个集合。

## 2 集合关系

User 1 ---- N Survey
Survey 1 ---- N Question
Survey 1 ---- N Response
User 1 ---- N Response

- 一个用户可以创建多份问卷。
- 一份问卷可以包含多个题目。
- 一份问卷可以收到多份答卷。
- 一个登录用户可以填写多份问卷。
- 问卷允许匿名时，系统内部仍保留填写者标识，但不向创建者展示。

## 3 users 集合

用途：保存注册用户和身份认证信息。

| 字段         | 类型     | 必填 | 说明                    |
| ------------ | -------- | ---- | ----------------------- |
| _id          | ObjectId | 是   | MongoDB 主键            |
| username     | String   | 是   | 用户名，唯一            |
| passwordHash | String   | 是   | bcryptjs 生成的密码哈希 |
| createdAt    | Date     | 是   | 注册时间                |
| updatedAt    | Date     | 是   | 更新时间                |

约束：

- username 去除首尾空格。
- username 长度为 3 至 30 个字符。
- username 建立唯一索引。
- 数据库不保存明文密码。
- 查询用户资料时默认不返回 passwordHash。

## 4 surveys 集合

用途：保存问卷基本信息、发布状态和填写规则。

| 字段                     | 类型     | 必填 | 说明                       |
| ------------------------ | -------- | ---- | -------------------------- |
| _id                      | ObjectId | 是   | 问卷主键                   |
| ownerId                  | ObjectId | 是   | 创建者，引用 users         |
| title                    | String   | 是   | 问卷标题                   |
| description              | String   | 否   | 问卷说明                   |
| allowAnonymous           | Boolean  | 是   | 是否匿名展示答卷           |
| allowMultipleSubmissions | Boolean  | 是   | 是否允许重复提交           |
| status                   | String   | 是   | draft、published 或 closed |
| publicId                 | String   | 是   | 公开访问码，唯一           |
| deadline                 | Date     | 否   | 截止时间                   |
| publishedAt              | Date     | 否   | 发布时间                   |
| closedAt                 | Date     | 否   | 关闭时间                   |
| schemaVersion            | Number   | 是   | 数据结构版本，默认 1       |
| createdAt                | Date     | 是   | 创建时间                   |
| updatedAt                | Date     | 是   | 更新时间                   |

索引：

- publicId 唯一索引，用于公开链接查询。
- ownerId 和 createdAt 组合索引，用于查询用户自己的问卷。
- status 和 deadline 组合索引，用于查询可填写问卷。

业务规则：

- draft 状态不能公开填写。
- published 状态且未超过截止时间时可以填写。
- closed 状态不能填写。
- publicId 不使用连续数字，避免被简单猜测。
- schemaVersion 为第二阶段的数据结构变化保留版本信息。

## 5 questions 集合

用途：保存题目、选项、校验配置和条件跳转规则。

| 字段       | 类型     | 必填 | 说明                                         |
| ---------- | -------- | ---- | -------------------------------------------- |
| _id        | ObjectId | 是   | 题目主键                                     |
| surveyId   | ObjectId | 是   | 所属问卷，引用 surveys                       |
| order      | Number   | 是   | 题目显示顺序                                 |
| type       | String   | 是   | singleChoice、multipleChoice、text 或 number |
| title      | String   | 是   | 题目内容                                     |
| required   | Boolean  | 是   | 是否必答                                     |
| options    | Array    | 否   | 单选和多选的选项                             |
| validation | Object   | 是   | 题目校验规则                                 |
| jumpRules  | Array    | 是   | 条件跳转规则                                 |
| createdAt  | Date     | 是   | 创建时间                                     |
| updatedAt  | Date     | 是   | 更新时间                                     |

选项结构：

| 字段     | 类型   | 说明               |
| -------- | ------ | ------------------ |
| optionId | String | 稳定的选项标识     |
| label    | String | 向填写者显示的文字 |

validation 可以包含：

| 字段          | 适用题型 | 说明           |
| ------------- | -------- | -------------- |
| minSelections | 多选     | 最少选择数量   |
| maxSelections | 多选     | 最多选择数量   |
| minLength     | 文本     | 最少字符数     |
| maxLength     | 文本     | 最多字符数     |
| minValue      | 数字     | 最小值         |
| maxValue      | 数字     | 最大值         |
| integerOnly   | 数字     | 是否必须为整数 |

jumpRules 中每条规则包含：

| 字段             | 类型     | 说明                                                 |
| ---------------- | -------- | ---------------------------------------------------- |
| operator         | String   | equals、containsAny、containsAll、gt、gte、lt 或 lte |
| value            | Mixed    | 用于比较的选项或数字                                 |
| action           | String   | goto 或 submit                                       |
| targetQuestionId | ObjectId | action 为 goto 时的目标题目                          |
| priority         | Number   | 多条规则命中时的优先级                               |

索引和约束：

- surveyId 和 order 建立唯一组合索引。
- type 只能使用系统支持的题型。
- 单选和多选题必须包含选项。
- 文本题和数字题不保存选项。
- targetQuestionId 必须属于同一份问卷。
- 保存问卷前检查跳转规则是否形成循环。

## 6 responses 集合

用途：保存每次成功提交的答卷。

| 字段                | 类型     | 必填 | 说明                 |
| ------------------- | -------- | ---- | -------------------- |
| _id                 | ObjectId | 是   | 答卷主键             |
| surveyId            | ObjectId | 是   | 所属问卷             |
| respondentId        | ObjectId | 是   | 实际填写者，内部使用 |
| anonymous           | Boolean  | 是   | 提交时是否匿名展示   |
| answers             | Array    | 是   | 答案列表             |
| visitedQuestionIds  | Array    | 是   | 实际访问的题目路径   |
| surveyVersion       | Number   | 是   | 提交时的问卷版本     |
| uniqueSubmissionKey | String   | 否   | 禁止重复提交时使用   |
| submittedAt         | Date     | 是   | 提交时间             |
| createdAt           | Date     | 是   | 创建时间             |
| updatedAt           | Date     | 是   | 更新时间             |

answers 中每项包含：

| 字段            | 类型     | 说明                         |
| --------------- | -------- | ---------------------------- |
| questionId      | ObjectId | 对应题目                     |
| questionType    | String   | 提交时的题型快照             |
| questionTitle   | String   | 提交时的题目文字快照         |
| value           | Mixed    | 实际答案                     |
| optionSnapshots | Array    | 单选或多选答案的选项文字快照 |

设计说明：

- respondentId 始终保存，用于登录校验和限制重复提交。
- anonymous 为 true 时，统计接口不能向创建者返回 respondentId。
- visitedQuestionIds 记录实际跳转路径，用于判断哪些必答题真正需要回答。
- 保存 questionType 和 questionTitle 快照，避免题目修改后旧答卷失去含义。
- 对于单选和多选题，value 保存稳定的 optionId 或 optionId 数组，
  optionSnapshots 保存提交时的 optionId 和 label。统计使用 optionId，
  查看旧答卷时使用快照中的 label，避免选项文字修改后旧答卷无法解释。
- 禁止重复提交时，uniqueSubmissionKey 使用 surveyId 和 respondentId 生成。
- 允许重复提交时，完全不创建 uniqueSubmissionKey 字段。
- 不能把 uniqueSubmissionKey 保存为 null，因为稀疏索引仍可能索引显式的 null。
- 数据保留与删除策略：
- 草稿问卷中的题目可以物理删除，因为草稿问卷尚未产生正式答卷。
- 问卷发布后不再物理删除题目，避免已有答卷引用的 questionId 失效。
- 已发布或已关闭的问卷不进行物理删除；需要停止填写时，将问卷状态改为 closed。
- 问卷关闭、超过截止时间或题目配置调整时，不级联删除已经保存的 responses。
- 已提交答卷及其中的题目和选项快照作为历史记录保留，用于统计、审计和第二阶段兼容旧数据。

## 7 统计设计

暂时不建立单独的 statistics 集合。

统计接口直接使用 MongoDB 聚合查询 responses：

- 单选题按照答案值分组计数。
- 多选题先展开数组，再按照选项分组计数。
- 文本题返回答案列表。
- 数字题使用平均值聚合计算平均数。

这样可以避免答卷数据与预计算统计数据不一致。数据量明显增大后，
第二阶段可以增加缓存或统计快照，而不改变原始答卷结构。

## 8 为什么使用独立 questions 集合

题目没有嵌入 surveys，原因如下：

- 可以单独添加、修改和排序题目。
- 条件跳转可以稳定引用 questionId。
- 问卷题目较多时，不会让 survey 文档持续膨胀。
- 第二阶段新增题型和规则时更容易扩展。
- 可以为 surveyId 和 order 建立组合索引。

代价是读取整份问卷时需要额外查询 questions，但可以通过一次按
surveyId 查询并按 order 排序完成，不需要逐题查询。

## 9 为什么适合 MongoDB

- 不同题型的 validation 内容不同，文档结构适合保存可选字段。
- 不同题型的答案 value 可以是字符串、数字或数组。
- jumpRules 可以作为规则数组保存，不需要建立大量关系表。
- responses 中的 answers 与一次提交共同创建和读取，适合嵌入数组。
- 后续新增题型和规则时，可以增加字段而不必重建固定关系表结构。

## 10 为什么不采用关系数据库结构

问卷题型的校验字段不同，答案也可能是字符串、数字或数组。
如果使用关系数据库，需要为题型、选项、校验规则、跳转条件和不同答案
建立多张表，并通过较多连接查询才能还原一份问卷或答卷。

MongoDB 可以把 validation、jumpRules 和一次提交的 answers 保存为嵌套文档，
数据结构与业务对象更接近。新增题型或规则时可以增加可选字段，
更适合第二阶段需求变化。

系统仍然使用多个集合和 ObjectId 引用，不把全部数据放进一个文档，
从而避免问卷文档无限增长。

## 11 冗余设计说明

系统只保留有明确用途的冗余数据：

- responses 保存 questionTitle 和 questionType 快照，保证题目修改后旧答卷仍可读。
- 选择题答案保存 optionId 和 label 快照，optionId 用于统计，label 用于显示。
- responses 保存 surveyVersion，标识提交时使用的问卷版本。

这些冗余字段在提交时一次写入，之后不跟随问卷修改，属于历史快照，
不需要与当前题目保持同步。

## 12 第二阶段扩展设计

- surveys 和 responses 保存版本字段。
- 题目类型和校验规则使用配置数据，而不是写死。
- 跳转规则使用 operator、action 和 value 描述。
- 答卷保存题目快照，保证旧数据可读。
- 新需求可以扩展 validation 和 jumpRules，而不删除旧字段。
- 需要迁移数据时记录迁移前后的版本和处理过程。



## 13 第二阶段数据库调整目标

第二阶段需要在保留第一阶段四个集合及旧数据的基础上，实现：

- 题目脱离问卷独立保存；
- 同一道题被多份问卷使用；
- 题目共享给其他用户；
- 题目版本历史；
- 多个版本同时存在；
- 查询题目被哪些问卷使用；
- 题目库；
- 单题跨问卷统计；
- 旧问卷、旧答卷和旧统计继续可用。

本阶段采用增量扩展方式，不删除第一阶段的 `users`、`surveys`、`questions` 和 `responses` 集合。

## 14 第二阶段集合关系

第二阶段的主要关系为：

    User 1 ---- N Survey
    User 1 ---- N QuestionItem
    User 1 ---- N QuestionBank

    QuestionItem 1 ---- N QuestionVersion
    QuestionItem 1 ---- N QuestionShare

    QuestionBank 1 ---- N embedded bank items

    Survey 1 ---- N Question
    QuestionItem 1 ---- N Question
    QuestionVersion 1 ---- N Question

    Survey 1 ---- N Response
    Response 1 ---- N embedded answers

其中：

- `QuestionItem` 表示逻辑上的同一道可复用题目；
- `QuestionVersion` 表示该题目的某个不可变版本；
- `Question` 继续表示题目在某份问卷中的具体使用实例；
- `QuestionBank` 用于组织可复用题目；
- `QuestionShare` 用于记录共享权限；
- `Response.answers` 保存问卷题目、逻辑题目和具体版本的引用及历史快照。

## 15 为什么保留 questions 集合

第一阶段的 `questions` 集合已经被以下数据和逻辑引用：

- `responses.answers.questionId`；
- `responses.visitedQuestionIds`；
- `jumpRules.targetQuestionId`；
- 题目编辑和删除接口；
- 公开问卷读取；
- 答案校验；
- 填写路径计算；
- 问卷内统计。

如果直接删除或重新生成 `questions`，会导致旧答卷、旧路径和跳转目标失效。

因此第二阶段保留原 `questions._id`，并把 `questions` 定义为“问卷题目实例或绑定记录”。

每条 `questions` 记录继续保存：

- 所属问卷；
- 问卷内顺序；
- 是否必答；
- 跳转规则；
- 题目内容快照；
- 校验配置快照。

同时新增对逻辑题目和题目版本的引用。

该设计存在少量冗余，但具有明确用途：

- 第一阶段旧接口可以继续读取原字段；
- 已发布问卷不会因公共题目产生新版本而变化；
- 旧答卷中的 `questionId` 不需要修改；
- 问卷读取不必逐题查询版本集合；
- 可以逐步迁移，不需要一次性重写所有业务代码。

## 16 questionItems 集合

### 16.1 用途

`questionItems` 表示逻辑上的一道题，是版本历史、共享、题目库和跨问卷统计的稳定入口。

题目标题和选项等可变化内容不直接保存在这里，而是保存在 `questionVersions` 中。

### 16.2 字段设计

| 字段                    | 类型     | 必填 | 说明                                    |
| ----------------------- | -------- | ---: | --------------------------------------- |
| `_id`                 | ObjectId |   是 | 逻辑题目标识                            |
| `ownerId`             | ObjectId |   是 | 所有者，引用 `users`                  |
| `currentVersionId`    | ObjectId |   否 | 当前推荐版本，引用 `questionVersions` |
| `latestVersionNumber` | Number   |   是 | 已分配的最大版本号                      |
| `status`              | String   |   是 | `active` 或 `archived`              |
| `legacyQuestionId`    | ObjectId |   否 | 第一阶段原题目标识，用于幂等迁移        |
| `schemaVersion`       | Number   |   是 | 数据结构版本，默认 1                    |
| `createdAt`           | Date     |   是 | 创建时间                                |
| `updatedAt`           | Date     |   是 | 更新时间                                |

### 16.3 业务规则

- 每个逻辑题目只能有一个所有者；
- `currentVersionId` 是新建问卷默认推荐使用的版本；
- 切换推荐版本不能修改已经绑定到问卷的版本；
- `latestVersionNumber` 只能增加，不能减小；
- 已存在历史版本的逻辑题目不进行物理删除；
- 停止使用时将 `status` 改为 `archived`；
- 归档不影响已经引用该题的问卷；
- 第一阶段迁移产生的逻辑题目保存 `legacyQuestionId`。

### 16.4 索引

```javascript
questionItemSchema.index(
  { ownerId: 1, createdAt: -1 }
);

questionItemSchema.index(
  { ownerId: 1, status: 1, updatedAt: -1 }
);

questionItemSchema.index(
  { legacyQuestionId: 1 },
  { unique: true, sparse: true }
);
```

`legacyQuestionId` 唯一稀疏索引用于保证迁移脚本重复运行时，不会为同一道旧题重复创建逻辑题目。

## 17 questionVersions 集合

### 17.1 用途

`questionVersions` 保存题目的具体内容。

版本创建后保持不可变。题目修改、历史恢复和基于旧版本编辑都通过创建新版本实现。

### 17.2 字段设计

| 字段                      | 类型     | 必填 | 说明                   |
| ------------------------- | -------- | ---: | ---------------------- |
| `_id`                   | ObjectId |   是 | 版本标识               |
| `questionItemId`        | ObjectId |   是 | 引用 `questionItems` |
| `versionNumber`         | Number   |   是 | 从 1 开始的版本号      |
| `parentVersionId`       | ObjectId |   否 | 直接来源版本           |
| `restoredFromVersionId` | ObjectId |   否 | 恢复操作复制的历史版本 |
| `createdByUserId`       | ObjectId |   是 | 创建者，引用 `users` |
| `changeNote`            | String   |   否 | 版本修改说明           |
| `type`                  | String   |   是 | 四种题型之一           |
| `title`                 | String   |   是 | 题目文字               |
| `options`               | Array    |   否 | 选择题选项             |
| `validation`            | Object   |   是 | 按题型保存的校验配置   |
| `schemaVersion`         | Number   |   是 | 版本文档结构版本       |
| `createdAt`             | Date     |   是 | 创建时间               |

### 17.3 不保存在版本中的字段

以下字段不保存在 `questionVersions` 中：

- `surveyId`；
- `order`；
- `required`；
- `jumpRules`。

原因是这些字段属于题目在具体问卷中的使用方式。

同一道题在问卷 A 中可以必答，在问卷 B 中可以选答；跳转目标也只能引用同一份问卷中的题目实例。

### 17.4 版本规则

- `versionNumber` 在同一 `questionItemId` 下唯一；
- v1 的 `parentVersionId` 为 `null`；
- 基于 v1 创建 v2 时，v2 的 `parentVersionId` 指向 v1；
- 恢复历史版本时仍然创建新版本；
- 恢复生成的版本同时记录直接父版本和 `restoredFromVersionId`；
- 历史版本不能原地更新；
- 被问卷使用的版本不能物理删除；
- 版本创建后只能补充非内容型审计信息，不能修改题型、标题、选项或校验规则。

### 17.5 选择题选项

每个选项继续包含：

| 字段         | 类型   | 说明           |
| ------------ | ------ | -------------- |
| `optionId` | String | 稳定的选项标识 |
| `label`    | String | 选项文字       |

创建新版本时：

- 含义未改变的选项保留原 `optionId`；
- 新选项生成新 `optionId`；
- 删除选项只影响新版本；
- 不允许同一版本中出现重复 `optionId`；
- 旧版本中的选项不随新版本变化。

### 17.6 索引

```javascript
questionVersionSchema.index(
  { questionItemId: 1, versionNumber: 1 },
  { unique: true }
);

questionVersionSchema.index(
  { questionItemId: 1, createdAt: -1 }
);

questionVersionSchema.index(
  { parentVersionId: 1 }
);
```

唯一组合索引用于保证同一逻辑题目不会出现两个相同版本号。

## 18 questionShares 集合

### 18.1 用途

`questionShares` 保存题目共享关系。

采用独立集合而不是在 `questionItems` 中保存无限增长的共享用户数组，便于：

- 查询共享给我的题目；
- 对共享用户建立唯一约束；
- 取消和恢复共享；
- 保留共享时间；
- 避免逻辑题目文档持续膨胀。

### 18.2 字段设计

| 字段                 | 类型     | 必填 | 说明                      |
| -------------------- | -------- | ---: | ------------------------- |
| `_id`              | ObjectId |   是 | 共享记录标识              |
| `questionItemId`   | ObjectId |   是 | 被共享的逻辑题目          |
| `sharedWithUserId` | ObjectId |   是 | 被共享用户                |
| `permission`       | String   |   是 | 当前阶段固定为 `use`    |
| `status`           | String   |   是 | `active` 或 `revoked` |
| `sharedAt`         | Date     |   是 | 首次共享时间              |
| `revokedAt`        | Date     |   否 | 取消共享时间              |
| `createdAt`        | Date     |   是 | 创建时间                  |
| `updatedAt`        | Date     |   是 | 更新时间                  |

### 18.3 权限规则

- 题目所有者不能把题目共享给自己；
- 同一题目与同一用户只保留一条共享记录；
- 被共享用户可以读取题目和版本；
- 被共享用户可以把版本加入自己的草稿问卷；
- 被共享用户不能修改或删除所有者的版本；
- 取消共享只阻止未来使用；
- 已经绑定到问卷的版本继续有效；
- 共享题目不能使题目所有者获得被共享用户的问卷或答卷权限。

### 18.4 索引

```javascript
questionShareSchema.index(
  { questionItemId: 1, sharedWithUserId: 1 },
  { unique: true }
);

questionShareSchema.index(
  { sharedWithUserId: 1, status: 1, updatedAt: -1 }
);

questionShareSchema.index(
  { questionItemId: 1, status: 1 }
);
```

## 19 questionBanks 集合

### 19.1 用途

`questionBanks` 保存用户建立的题目库。

题目库规模预计有限，并且题库详情通常需要一次读取全部条目，因此题库条目作为嵌入数组保存。

### 19.2 字段设计

| 字段            | 类型     | 必填 | 说明                       |
| --------------- | -------- | ---: | -------------------------- |
| `_id`         | ObjectId |   是 | 题目库标识                 |
| `ownerId`     | ObjectId |   是 | 所有者                     |
| `name`        | String   |   是 | 题目库名称                 |
| `description` | String   |   否 | 题目库说明                 |
| `status`      | String   |   是 | `active` 或 `archived` |
| `items`       | Array    |   是 | 题库条目                   |
| `createdAt`   | Date     |   是 | 创建时间                   |
| `updatedAt`   | Date     |   是 | 更新时间                   |

每个 `items` 元素包含：

| 字段                   | 类型     | 必填 | 说明         |
| ---------------------- | -------- | ---: | ------------ |
| `questionItemId`     | ObjectId |   是 | 逻辑题目     |
| `preferredVersionId` | ObjectId |   否 | 题库推荐版本 |
| `order`              | Number   |   是 | 题库中的排序 |
| `addedAt`            | Date     |   是 | 加入题库时间 |

### 19.3 业务规则

- 用户只能管理自己的题目库；
- 同一题库中不能重复加入同一个逻辑题目；
- 加入共享题目前必须检查有效共享权限；
- 更新 `preferredVersionId` 不影响已发布问卷；
- 从题库移除题目不删除逻辑题目或版本；
- 归档题目库不影响已经创建的问卷；
- 题目库暂不共享给其他用户；
- 如果题目库规模明显增大，可在后续阶段拆分独立的题库条目集合。

### 19.4 索引

```javascript
questionBankSchema.index(
  { ownerId: 1, name: 1 },
  { unique: true }
);

questionBankSchema.index(
  { ownerId: 1, status: 1, updatedAt: -1 }
);

questionBankSchema.index(
  { 'items.questionItemId': 1 }
);
```

同一题库中的重复题目由 Schema 校验和业务逻辑共同阻止。

### 20.3 新建绑定流程

从题目库或题目列表向草稿问卷添加题目时：

1. 检查问卷属于当前用户；
2. 检查问卷状态为 `draft`；
3. 检查用户拥有题目或具有有效共享权限；
4. 读取指定 `questionVersionId`；
5. 创建新的 `Question` 问卷题目实例；
6. 保存 `questionItemId` 和 `questionVersionId`；
7. 将版本的题型、标题、选项和校验配置复制为问卷实例快照；
8. 单独设置 `order`、`required` 和 `jumpRules`。

该复制不是失控冗余，而是用于固定问卷内容和兼容第一阶段代码的历史快照。

### 20.4 跳转规则

`jumpRules.targetQuestionId` 继续引用同一问卷中的 `Question._id`，不引用 `QuestionVersion._id`。

原因是跳转发生在某份问卷的具体题目实例之间，而不是公共题目版本之间。

```javascript

  { questionVersionId: 1, surveyId: 1 }
);

  { surveyId: 1, questionVersionId: 1 }
```

- 完成题目引用迁移的问卷更新为版本 2；

## 23 是否建立题目使用情况集合

不新增独立的 `questionUsages` 集合。

题目使用情况直接查询 `questions`：

- 按 `questionItemId` 查询逻辑题目的全部使用实例；
- 按 `questionVersionId` 查询某版本的使用实例；
- 根据 `surveyId` 关联问卷标题、所有者和状态。

这样可以避免出现问卷已经删除题目绑定，但使用情况集合没有同步的问题。

## 24 是否建立跨问卷统计集合

第二阶段暂不建立独立的跨问卷统计集合。

跨问卷统计直接从 `responses.answers` 聚合：

1. 先确定当前用户有权统计的问卷；
2. 按 `questionItemId` 或 `questionVersionId` 匹配答案；
3. 展开 `answers`；
4. 根据题型执行分组、列表或数字聚合；
5. 按版本返回明细；
6. 不返回填写者身份字段。

这种设计以原始答卷为统计事实来源，不会产生统计缓存与答卷不一致的问题。

如果未来数据量明显增加，可以增加可重建的统计缓存，但不能代替原始答卷。

## 25 版本创建和并发控制

创建新版本时需要防止两个请求得到相同版本号。

推荐流程：

1. 验证当前用户是题目所有者；
2. 使用原子更新增加 `latestVersionNumber`；
3. 取得新的版本号；
4. 创建 `questionVersions` 文档；
5. 更新 `currentVersionId`；
6. 如果创建版本失败，记录错误并允许安全重试；
7. 由唯一索引阻止重复版本号。

如果 MongoDB 部署支持事务，可以在事务中完成版本创建和当前版本更新。

项目在单机 MongoDB 环境运行时，仍必须依靠唯一索引和幂等重试保证一致性。

## 26 删除和归档策略

### 26.1 逻辑题目

- 没有任何版本和引用的错误测试数据可以物理删除；
- 正式逻辑题目使用 `archived` 状态；
- 归档后不能加入新问卷；
- 已存在问卷引用继续有效。

### 26.2 题目版本

- 被任何问卷引用的版本不能删除；
- 历史版本不物理删除；
- 创建错误且从未被使用的版本是否允许删除，需要由业务规则严格限制；
- 默认采用保留历史版本的策略。

### 26.3 问卷题目实例

继续采用第一阶段规则：

- 只能删除草稿问卷中的题目实例；
- 被跳转规则引用时不能删除；
- 已发布和已关闭问卷中的实例不删除。

### 26.4 题目库

- 从题目库移除条目不删除题目；
- 题目库使用 `archived` 状态；
- 归档题库不影响问卷和题目版本。

### 26.5 共享关系

- 取消共享将状态改为 `revoked`；
- 不删除历史共享记录；
- 已经加入问卷的版本继续有效。

## 27 第一阶段旧数据迁移方案

### 27.1 迁移原则

迁移只增加新集合和新字段，不删除第一阶段字段。

迁移必须：

- 可重复运行；
- 可以在测试数据库演练；
- 记录处理数量；
- 保留旧 `_id`；
- 保留旧快照；
- 保留旧公开链接；
- 保留旧答卷；
- 保留旧跳转目标；
- 支持迁移失败后继续运行。

### 27.2 迁移前准备

迁移前执行：

1. 备份 `questionnaire_system` 数据库；
2. 记录四个旧集合的文档数量；
3. 运行第一阶段完整测试；
4. 检查所有题目的 `surveyId`；
5. 检查所有答卷答案的 `questionId`；
6. 检查所有 `visitedQuestionIds`；
7. 检查所有跳转目标；
8. 建立测试数据库副本；
9. 先在测试数据库运行迁移。

### 27.3 题目迁移

对每条第一阶段 `Question`：

1. 根据 `surveyId` 查询问卷；
2. 取得问卷的 `ownerId`；
3. 使用原 `Question._id` 查询 `questionItems.legacyQuestionId`；
4. 如果已经存在，则复用，不能重复创建；
5. 如果不存在，创建一个 `QuestionItem`；
6. 创建该逻辑题目的 v1；
7. v1 复制原题目的 `type`、`title`、`options` 和 `validation`；
8. 将 `QuestionItem.currentVersionId` 指向 v1；
9. 将原 `Question` 补充 `questionItemId`；
10. 补充 `questionVersionId`；
11. 设置 `contentSource` 为 `legacy`；
12. 设置 `schemaVersion` 为 2；
13. 保留原 `Question._id`、`surveyId`、`order`、`required` 和 `jumpRules`。

迁移不会根据题目文字自动合并旧题。

即使两份旧问卷中都有“你的年龄”，也不能仅凭标题推断它们是同一道逻辑题目。每条旧题默认生成独立的逻辑题目，避免错误合并数据。

### 27.4 答卷迁移

对每条 `Response.answers`：

1. 根据 `answer.questionId` 查询原 `Question`；
2. 读取该题的 `questionItemId`；
3. 读取该题的 `questionVersionId`；
4. 将两个引用写入答案；
5. 保留原 `questionId`；
6. 保留 `questionType`；
7. 保留 `questionTitle`；
8. 保留 `value`；
9. 保留 `optionSnapshots`。

完成全部答案迁移后，将 `Response.schemaVersion` 更新为 2。

`visitedQuestionIds` 不修改，因为其中保存的仍然是原 `Question._id`。

### 27.5 问卷版本迁移

只有当问卷中的全部题目都存在有效的：

- `questionItemId`；
- `questionVersionId`；

才能把 `Survey.schemaVersion` 从 1 更新为 2。

如果某道题迁移失败，该问卷保持版本 1，并记录失败原因。

### 27.6 迁移记录

建议增加 `schemaMigrations` 集合：

| 字段               | 类型   | 说明                         |
| ------------------ | ------ | ---------------------------- |
| `name`           | String | 迁移名称，唯一               |
| `status`         | String | running、completed 或 failed |
| `startedAt`      | Date   | 开始时间                     |
| `completedAt`    | Date   | 完成时间                     |
| `processedCount` | Number | 处理数量                     |
| `skippedCount`   | Number | 跳过数量                     |
| `failedCount`    | Number | 失败数量                     |
| errorDetails       | Array  | 精简错误记录                 |

迁移名称可以使用：

`stage2-question-versioning-v1`

为 `name` 建立唯一索引，避免重复启动相同迁移任务。

### 27.7 幂等要求

迁移脚本重复执行时：

- 已存在 `legacyQuestionId` 的逻辑题目不重复创建；
- 已有 v1 不重复创建；
- 已有引用不重复写入；
- 已迁移答案不重复处理；
- 文档数量不随重复运行增长；
- 迁移结果保持一致。

## 28 迁移后验证

迁移后至少检查：

- 用户数量保持不变；
- 问卷数量保持不变；
- 原 `questions._id` 保持不变；
- 答卷数量保持不变；
- 每条题目都有逻辑题目和版本引用；
- 每条答案都能映射到题目版本；
- 每个 `visitedQuestionIds` 都能找到原题；
- 每个跳转目标仍属于同一问卷；
- 第一阶段公开链接仍能访问；
- 已发布问卷内容与迁移前一致；
- 问卷内统计结果与迁移前一致；
- 匿名字段保护继续有效；
- 重复提交保护继续有效；
- 第一阶段 Jest 测试全部通过；
- 迁移脚本第二次运行不会新增重复数据。

## 29 回滚和兼容策略

迁移采用增加字段和集合的方式，不立即删除第一阶段字段。

如果第二阶段代码出现问题：

- 可以切回 `stage1-final` 查看第一阶段代码；
- 第一阶段代码仍可以读取原 `questions` 内容字段；
- 原 `questionId` 和跳转目标没有改变；
- 原答卷快照没有改变；
- 新集合不会阻止旧代码读取原数据；
- 数据库备份可以用于恢复迁移前状态。

在第二阶段最终验收前，不删除第一阶段兼容字段。

## 30 数据权限总结

| 数据         | 可管理用户             | 可读取用户                             |
| ------------ | ---------------------- | -------------------------------------- |
| 问卷         | 问卷所有者             | 所有者；已发布问卷允许公开读取必要字段 |
| 逻辑题目     | 题目所有者             | 所有者和有效共享用户                   |
| 题目版本     | 题目所有者创建         | 所有者和有效共享用户                   |
| 共享记录     | 题目所有者             | 所有者及与本人相关的共享用户           |
| 题目库       | 题目库所有者           | 题目库所有者                           |
| 问卷题目实例 | 问卷所有者             | 根据问卷状态和接口权限读取             |

| 跨问卷统计   | 有权管理对应问卷的用户 | 当前阶段仅限本人有权统计的问卷         |

## 31 第二阶段设计验收标准

数据库设计满足以下条件时才能进入代码实现：

- 保留第一阶段四个集合及旧数据；
- 原 `Question._id` 不发生变化；
- 逻辑题目和具体版本分离；
- 问卷配置与公共题目内容分离；
- 问卷固定绑定具体版本；
- 已发布和已关闭问卷内容不可变；
- 共享权限不能扩大问卷和答卷权限；
- 题目库移除题目不删除历史数据；
- 版本恢复通过创建新版本完成；
- 使用情况可以从 `questions` 查询；
- 跨问卷统计可以从 `responses.answers` 聚合；
- 旧答卷继续保存快照；
- 迁移过程幂等；
- 第一阶段测试可以继续运行；
- 所有新增索引均有明确查询用途；
- 没有依靠题目标题判断同一道题；
- 没有建立容易与原始数据失去同步的统计结果集合。
